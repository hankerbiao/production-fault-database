# 销售订单统一判定 5000 公司实施方案

> 2026-10-28 更新：历史数据暂不处理，下文关于历史迁移和重算的内容仅保留为原设计记录。

**目标：** 仅由销售订单同步使用产品层次 `00100`；非 SCS 数据源根据 MongoDB 销售订单表中的订单号判定 5000 公司。

**架构：** 销售订单集合是归属的权威正向名单；各数据源通过统一的订单存在性接口关联。归属、订单字段补全和历史数据迁移分开处理，未知数据可重试；SCS 沿用现有处理链路。

**技术栈：** Python、MongoDB/PyMongo、SAP HTTP/HANA、Go API、pytest。

## 一、规则和边界

1. 销售订单同步请求继续传 `PRODH_LIST=["00100"]`；来源返回明确非 `00100` 时拒绝该明细。响应缺少 `PRODH` 时，仅对通过已确认可靠的过滤接口获取的记录按该过滤结果处理。销售表完整性和过滤可靠性须在切换前审计。
2. 非 SCS 数据含生产订单号或销售订单号：任一规范化后的号码存在于销售订单表，即判定为 5000 公司；仅存在一条记录即可，不要求订单号映射唯一。两种号码都存在但指向不同订单时仍按存在规则判定，记录冲突，不据此自动补全或改写号码。
3. 没有订单号、没有匹配、订单表不可用、订单历史覆盖不足均不能推断非 5000；记录为待核对/待重试。除有其他明确权威来源外，不生成 `false`。
4. 号码按现有 `order_key` 去空白、数字前导零；字母大小写及非数字内容沿用现有行为。应确认来源、`MANDT` 是否构成订单号命名空间：有明确且可信的客户端时优先限定；跨来源同号时归属可按存在判断，但字段补全必须唯一。不能为满足唯一性而让已存在订单变成未匹配。
5. SCS 的采集、筛选、XNC/CPX 规则与数据迁移不纳入；共享函数、过滤器、检查点和参数改造必须保持 SCS 现状，添加回归测试。

## 二、数据流

```text
SAP 销售接口 -- PRODH_LIST=[00100] --> MongoDB sales_orders_sap
                                             |
                            销售订单号或生产订单号存在
                                             |
          工位 / 维修 / BOM / 序列号 --> 已匹配 / 待核对
                                             |
                          看板、统计、导出读取统一结果
```

### 关联字段

| 数据源 | 生产订单 | 销售订单 | 特殊处理 |
|---|---|---|---|
| 工位 | `AUFNR` | `KDAUF` | 工位无订单号不得仅凭旧范围标记认定 |
| 维修 | `AUFNR` | `VBELN` | 可先查主机关系补订单号，归属最终查销售表 |
| BOM | `AUFNR_1` | `VBELN_EX` | 不用 `CPX` 决定归属或删除 |
| 序列号绑定 | `AUFNR_HEAD` | 无 | 以主机订单为准；组件订单不替代主机订单 |

同步任务保留“销售订单先于各下游”的现有依赖。单独执行下游时也应检查销售表可用及已完成的同步范围；表为空或不可访问时失败并保留检查点，不把数据批量认定为非 5000。

## 三、实现步骤

### 1. 审计销售订单名单并确认覆盖范围

- 涉及 `scripts/sync/sync_sales_orders.py`、`scripts/sales_order_reference.py`、`scripts/sync/README.md`。
- 对现有集合做只读审计：按来源、时间范围、明细 `PRODH`（00100 / 非 00100 / 缺失）、销售订单号、生产订单号统计，并报告历史覆盖起止、重复及冲突。不能把 `PRODH` 缺失直接视为异常；但必须有可信的来源过滤证据。
- 对可疑存量先从来源重新核验；未核验前不得将其作为权威正向名单。不得因本次审计直接删除订单。
- 现有订单结构按生产订单聚合，关联必须遍历 `records` 和 `data`，避免只查最后一条明细漏掉销售订单号。销售看板的 5000 筛选与该集合口径一致；如果选择增加显式标记，应由销售同步写入，历史标记只在核验后回填，不要求下游重查 `PRODH`。

### 2. 建立非 SCS 专用订单存在性接口

- 修改 `scripts/sales_order_reference.py`，新增与现有 `resolve` 分离的存在性接口，避免改变 SCS 的调用语义；返回 `matched` 或 `pending`，并携带匹配字段、规范化订单号、来源及冲突信息。匹配判断分别查生产和销售索引后取并集，而不是对两者做交集。
- 保留专门用于字段补全的唯一映射逻辑。匹配多个订单时仍可判定为 5000，但不能随意选择销售订单、生产订单或计划日期补写。
- 分批读取已核验的销售订单索引；先复用现有进程内索引，记录行数、耗时和内存；若数据量超出资源预算，再依据实测选择 MongoDB 索引及批量查询。禁止逐条扫描销售集合。
- 修改 `tests/test_sales_order_reference.py`，覆盖销售号或生产号单独命中、两个字段只有一个命中、同时命中不同订单、一个销售号对应多个生产号、数字前导零、空值和跨来源同号；另验证旧 SCS 调用行为不变。

### 3. 工位、BOM、序列号

- 修改 `scripts/sources/hana/hana_view_sync.py` 和 `scripts/table_pipeline.py`：工位及 BOM 与序列号一样调用新的存在性接口；读取数据与归属标记分开，保留未知原始数据并进入 `sync_scope_pending` 或等价待处理机制，以支持后续重试。
- 修改 `scripts/maintenance/clean_order_boards.py`：停止用 BOM `CPX` 判定或删除公司数据；保留 `CPX` 原始字段供展示。订单号补全仍要求唯一关系。维护脚本与日常同步必须共用同一归属规则。
- 范围标记采用独立的非 SCS 规则版本和匹配依据；在完成后端切换之前兼容现有 `_prodh_scope` 消费方。该标记只表示已关联销售表，不重新检查其他表的 `PRODH`。切勿修改 SCS 所用共享标记的含义。
- 更新 `tests/test_station_sync_unscoped.py`、`tests/test_hana_view_sync.py`、`tests/test_clean_order_boards.py`、`tests/test_bom_scope_matching.py`、`tests/test_sync_admission.py`：检查命中、未命中、重试及 BOM 非目标 CPX 但订单已命中时不会被删除。

### 4. 维修及补全

- 修改 `scripts/sync/sync_sales_orders.py` 的 `sync_repair`，通过新存在性接口判定；缺少两个订单号时，主机/工位只能作为查找订单号的线索，不得把工位旧 `_prodh_scope` 单独当作归属证明。
- 修改 `scripts/sync/增量同步和清洗维修故障记录.py`：SAP 序列号查询不得使用 `00100` 做归属过滤；先确认接口支持不带该过滤的查询。若不支持，则停用该补全路径并将记录保留待核对，不能假定接口可用。任何返回订单号均须通过销售表确认。
- 调整 `tests/test_repair_snapshot.py`、`tests/test_backfill_repair_orders_from_station.py`：覆盖关联、空号码、站点旧标记、SAP 补全和未命中重试。

### 5. 看板、同步状态与 SCS 隔离

- 在 `backend/internal/store/filters.go`、`store.go`、`faults.go`、`orders.go` 中按数据集区分范围过滤；非 SCS 看板、统计和导出统一使用匹配结果，SCS 原有过滤不变。核查 `views.go`、`stream.go`、`export.go` 的同一过滤链。
- 维修筛选不能使用 `$nin` 把未匹配、缺号归入“非 5000”。保留既有 API 参数兼容，但在无可靠负向依据时 `no` 不返回待核对数据；文档明确当前名单只能确认正向。
- 对销售表来源同步失败、过期和覆盖范围不足提供可观测状态。检查 `scripts/sync/syncctl.py` 与任务注册表；不要将 SCS 的依赖、检查点或现有发布逻辑误改。现有发布账本不是数据库快照隔离，切换前需验证读取期间的一致性，不能仅凭 ready 标记承诺原子发布。
- 更新 `backend/internal/store/store_test.go`、相关集成测试及 `docs/openapi.json` / API 文档，覆盖列表、统计、导出、未知和 SCS 现有行为。

### 6. 历史数据、增量及回滚

- 先以只读预览输出每个集合的总数、正向匹配、缺号、未匹配、冲突、按旧 CPX 删除与新规则不一致的候选；审计销售订单历史覆盖，确认数据源日期范围后再推进。
- 将来源版本、匹配依据、订单关联键和时间保存为独立标记；对存量采用可重复、分批、可中断的回填，记录每批进度。未匹配进入待核对队列，不删除原始记录；销售订单新增或变更时重新处理相关记录，包括已匹配记录的失效及补录，不能只依赖原始数据的增量水位。需要按订单键建立反向查找索引，或提供可控的分批重新核对任务。
- 先双写新旧标记并比较看板结果，再在验证通过后切换非 SCS 查询。回滚使用旧版本代码和保留的旧标记；切换和回滚期间确保 SCS 查询、数据及检查点不变。保留源快照及运行日志；新旧字段不要在验证前删除。
- 增量任务发生关联错误、写入失败或销售表不可用时不得推进相关检查点；通过待处理机制避免源水位推进后永久漏数。历史订单不在销售表中时显示待核对，不宣称是非 5000。

## 四、验收和验证

1. 销售订单同步请求包含 `00100`；非 SCS 来源的公司判断没有使用自身 `PRODH` 或 BOM `CPX`，维修 SAP 补全不再发送该产品过滤。
2. 销售号或生产号任一存在即匹配；双号冲突和一对多匹配不会阻止正向归属，但不自动补错字段。
3. BOM `CPX` 不符合旧规则但订单已匹配时保留；未匹配/缺号记录可恢复、可重试、不进入非 5000 统计。
4. 销售订单后到、变更、失效、同步失败、重启后，待处理和已匹配数据均能重新核对；检查点及看板状态如实反映处理结果。
5. 工位、维修、BOM、序列号的列表、统计、导出同口径；SCS 同步与查询回归结果不变。
6. 在项目虚拟环境运行对应测试，例如 `.venv/bin/python -m pytest tests/test_sales_order_reference.py tests/test_sync_admission.py tests/test_hana_view_sync.py tests/test_station_sync_unscoped.py tests/test_clean_order_boards.py tests/test_bom_scope_matching.py tests/test_repair_snapshot.py tests/test_backfill_repair_orders_from_station.py tests/test_scs_doa_sync.py tests/test_scs_change_sync.py`；在 `backend` 目录运行 `go test ./internal/store ./cmd/server`。测试命令以实际环境及 MongoDB 集成测试条件为准。

## 五、实施前需确认

- 订单号在 SG、KK 及不同 `MANDT` 中是否可能重复且代表不同订单；这影响跨来源命中策略和冲突报告。
- 销售订单接口的过滤可靠性、历史覆盖起点，以及维修 SAP 序列号接口是否支持不带 `PRODH_LIST`。
- 现有看板是否需要展示待核对记录；默认只在同步运行状态提供待核对统计，不把它们混入 5000 公司结果。
