## 优先级

- P1：应优先修复，可能误删、并发覆盖、漏同步，或让任务与页面长期处于错误状态。

## 已确认的问题

### 1. [P1] SCS 不完整读取被当作完整结果，可能触发误删

位置：`scripts/sources/scs_doa_sync.py:226`、`:396`、`:473`；`scripts/sources/scs_change_sync.py:178`、`:312`、`:351`。

DOA 第二页及以后的 ReadTimeout 会结束分页并返回已有行。上层仍设置 `success=True`，全量模式删除未被本次标记的文档，最后提交 completed 检查点。离线复现：第一页 1 行、第二页超时，本地未抓到的 1 行被删除，任务仍报告成功。

两个 SCS 解析器也没有区分“有效的空结果表”与“登录页/异常 HTML”。会话过期后返回 HTTP 200 的登录页时，解析结果为空，上层可能当作分页结束。离线模拟确认两种解析器都把登录页解析为 `[]`。

建议：分页失败必须失败退出；验证登录状态、目标表、必需列和合法空结果；只有完整读取且完成校验的快照才能清理。增加空源保护、删除比例保护和归档恢复能力。预览也应报告源完整性。

### 2. [P1] HANA full 的清理范围超出读取窗口，空结果也可清空集合

位置：`scripts/sources/hana/hana_view_sync.py:503`、`:522`；`scripts/table_pipeline.py:144`。

工位/BOM 的源查询接受开始和结束日期，但两处全量提交都只按 `_source_view` 和非本次 `_sync_run_id` 删除，没有限制日期。例如只重建 2026 年 9 月，1 月数据也会被删除。全量读取为空且没有异常时也进入同样的删除阶段。

离线复现：提交仅包含 9 月的 full 结果，删除 1 月记录；提交 source_rows=0 的 full 结果，清空已有源数据。交付明细的全量预检只检查键冲突，不能阻断空结果。

建议：提交显式保存并校验读取范围；窗口对账仅清理窗口内记录，整集合替换另用显式参数；清洗也使用同一范围。删除前校验源完整性、写入覆盖量和删除比例，并先归档。维修快照已有相近保护，可复用原则和小型公共组件。

### 3. [P1] 直接执行与编排执行的锁覆盖范围不一致

位置：`scripts/sync/sync_sales_orders.py:618`；`scripts/sources/scs_doa_sync.py:380`；`scripts/sources/scs_change_sync.py:213`；`scripts/maintenance/backfill_order_bom_planned_start.py:335`。

销售订单和两个 SCS 入口没有任务级锁。编排器锁只能互斥编排器，不能阻止直接执行这些入口。两个 full 并发时，各自的 run_id 清理会删除另一个运行写入的数据，检查点也可能相互覆盖。

BOM 回填与 BOM 同步使用不同任务锁，直接运行回填时也可与同步竞争同一集合。

建议：每个可执行入口都使用相同公共锁组件；锁名按实际写入资源定义，编排器保持流程锁。派生回填与源同步共享对应集合的互斥规则，避免仅按脚本名加锁。

### 4. [P1] 租约续租异常不触发失锁保护，子进程也不会及时停止

位置：`scripts/sync/syncctl.py:178`、`:274`、`:293`；`scripts/sources/hana/hana_view_sync.py:231`。

编排器续租线程遇到 MongoDB 异常直接退出，没有设置 lost。离线模拟续租 update_one 抛 connection lost 后，`lease.lost` 仍为 False。租约过期后其他运行可进入，旧运行仍写数据。

即便 matched_count=0 设置了 lost，也只在下一任务开始前检查；当前同步子进程继续运行。公共任务租约默认 12 小时，不续租也不校验持有者，超过期限后存在相同风险。

建议：统一可续租的锁实现，捕获续租异常并标记失锁；父进程检测失锁时终止并回收子进程组；清理/提交前再次校验持锁权。任务期限与租约期限分别配置。

### 5. [P1] 编排器有租约心跳，却没有持续更新运行记录心跳

位置：`scripts/sync/syncctl.py:206`、`:221`、`:269`、`:293`。

RunStore.heartbeat 定义了但没有调用。大多数阶段只在启动/结束时更新 heartbeat_at；BOM 回填是单独写进度的例外。其他任务超过默认 300 秒后，新启动的编排器会在获取租约前把仍工作的旧运行标记 abandoned，随后自己因为锁冲突退出。

此外 subprocess.run 没有任务超时；子进程挂起时父进程可以一直续租，所有后续任务被阻塞。未预期的异常也可能绕过 finish，留下一条 running 记录。

建议：父进程在等待任务时持续写运行心跳、检查租约和期限；先确认失活再标 abandoned；所有退出路径记录最终状态并回收子进程。实时日志写文件，摘要保留有界尾部。

### 6. [P1] 工位增量没有实际应用回看天数，会漏掉迟到历史记录

位置：`scripts/sources/hana/hana_view_sync.py:371`、`:378`。

回看仅对 BUDAT_MKPF 和 ERDAT 生效；工位 ACTUAL_START_TIME 使用原水位。设置 `--lookback-days 7` 后，离线构造 SQL 的下界仍为原始 `2026-10-14 10:00:00`。若后来落库的记录实际开始时间早于该水位，将不再被读取。

建议：对时间戳水位实施真实回看，统一日期/时间类型转换。开始时间和创建日期都不等于修改时间，超过回看期的更正仍需定期窗口或全量对账。

### 7. [P1] cron 同步交付明细后不会刷新看板物化汇总

位置：`scripts/sync/sales_order_delivery_records.py:71`；`backend/cmd/server/main.go:37`；`backend/cmd/server/sync.go:131`；`backend/internal/store/views.go:53`。

后端启动时初始化汇总；当前初始化实现允许复用已有汇总，API 发起的整次同步成功后另有刷新回调。每天 19:00 直接运行 Python 的 cron 不经过该回调。后台服务长期运行时，无筛选交付看板读取旧汇总，带筛选查询读取新明细，结果可能不一致；仅重启后端也不保证刷新已存在的汇总。

即使 API 发起，交付任务成功但后面的 SCS 失败时，也不会执行该回调。

建议：以交付数据版本/任务完成事件触发刷新，持久化源版本和汇总版本；cron、API、CLI 共用同一完成契约。后端可检测版本变化并沿用现有 Go 汇总实现，避免另写一套 Python 聚合规则。

### 8. [P2] dry-run 并非一致的只读预览，而且预览不等于正式执行范围

位置：`scripts/table_pipeline.py:117`、`:161`；`scripts/sources/hana/hana_view_sync.py:462`；`scripts/sources/scs_change_sync.py:224`；`scripts/sync/增量同步和清洗维修故障记录.py:659`。

工位/BOM/序列号 dry-run 仍创建租约/索引并写 sync_runs。离线模拟返回 dry_run=True，同时新增 1 条运行记录。BOM 回填预览也获取 MongoDB 租约。

HANA 和 SCS 换上换下预览不读取已有检查点，读取窗口与 apply 不同。维修预览读取源快照后释放它，后续回填只分析本地旧记录；新源记录的回填结果不能在这次预览里体现。

建议：预览允许读取检查点，禁止数据库写入；明确区分源扫描统计和待提交变更。维修应在临时快照上计算回填计划，供预览和 apply 共用。

### 9. [P2] 销售订单等错误输出无法触发编排器的瞬时故障重试

位置：`scripts/sync/sync_sales_orders.py:690`；`scripts/sync/syncctl.py:250`、`:303`；两个 SCS 脚本的主入口。

销售订单连接超时放在 sources.SG.error 中，顶层没有 error。编排器只检查顶层 error，离线模拟此摘要的 retryable=False，因而不会重试。SCS 未统一捕获异常输出结构化错误，可能被归为 invalid_script_output 而失去原始可重试信息。

建议：所有入口统一 success、error.code、error.message、error.retryable、partial_writes 和计数结构；按异常类型分类。任务脚本负责请求级重试，编排器仅处理少量任务级重试，避免叠加大量重复请求。

### 10. [P2] 日期参数与配置存在行为差异，降低可用性

位置：`scripts/sync/syncctl.py:51`、`:74`；`scripts/sync/sync_sales_orders.py:84`；`scripts/table_pipeline.py:36`、`:98`；`scripts/maintenance/clean_order_boards.py:78`。

- 增量销售订单和两个 SCS 任务不接收编排器 end-date，运行记录所列日期与实际范围可能不同。交付明细固定 2026 范围是已明确设计，应继续在任务元数据中体现。
- 销售订单自建 mongo_uri，不支持公共实现已支持的 MONGODB_URI。离线模拟只配 URI，编排器能连接，销售任务却报 MONGODB_HOSTS 未配置。
- 三个 HANA 包装入口在读取 .env 之前构建 parser，.env 的批大小/回看值不进入参数默认值。
- BOM 预览日期过滤使用 YYYY-MM-DD，源 BUDAT_MKPF 采用 YYYYMMDD，范围比较不能正确对应。
- HANA ViewSpec 集合名固定，而维修/回填/独立清洗会读取 STATION_COLLECTION、BOM_COLLECTION；更改集合配置时，同步与回填可能操作不同集合。

建议：启动时加载一次配置并校验；公共 URI、集合解析和源字段日期编码共用。任务元数据声明日期和模式能力，不支持的覆盖明确拒绝。

### 11. [P2] SCS 恢复使用位置偏移，源列表变化时可能漏行

位置：`scripts/sources/scs_doa_sync.py:394`、`:403`；`scripts/sources/scs_change_sync.py:228`、`:247`、`:315`。

DOA 恢复重新抓取全表，然后跳过保存的行索引；换上换下恢复保存页码和页内偏移。查询没有展示稳定唯一排序/固定快照契约；若恢复前新增、删除或重新排序，偏移指向的业务记录会变化。

两个脚本处理旧详情的机制也不能保证最终修复：DOA 详情失败仍成功推进水位，记录退出回看窗口后未必再重试；详情更新失败还可能用 error 替换旧的有效 details。服务页和产品页没有 raise_for_status。

建议：有源游标时使用稳定唯一键恢复；否则固定范围、允许重叠重读，并以业务键去重，失败快照禁止删除。详情维护独立待补队列，保留最后成功详情和本次错误。

### 12. [P2] SCS 公司归属的派生字段不会一致地随依赖变化更新

位置：`scripts/sources/scs_doa_sync.py:367`；`scripts/sources/scs_change_sync.py:274`、`:324`。

DOA 会重算所有历史记录的公司归属，换上换下只重算本次读到的记录。销售订单变化或 DOA 详情补齐后，回看窗口之外的换上换下记录会保留旧分类。

DOA 全表回填的投影没有 is_5000_company，比较时该字段始终读不到；即使值已一致也会生成写操作，增加日常全表写入负担。

建议：按受影响服务单重算换上换下历史分类；源同步和派生字段重算分别记录版本/状态。投影包含所有比较字段，只写变化。

### 13. [P2] 批量参数不能稳定限制内存，且包含不必要写入

位置：`scripts/maintenance/backfill_order_bom_planned_start.py:223`、`:243`、`:267`、`:289`；`scripts/maintenance/clean_order_boards.py:169`、`:264`；`scripts/table_pipeline.py:65`。

BOM 回填在空订单/未匹配分支先累积规范化操作再 continue，跳过批量刷写判断。离线模拟 batch_size=3、10 条这样的记录，最后单批写入 10 条。已标 unchanged 的记录仍加入 UpdateOne；模拟 1 条不变数据，write_attempted 仍为 1。

工位/BOM 清洗先把全部动作收进列表，再分批执行；序列号去重把全部业务键及 ID 放进内存。DOA 全表读取和全量 `$in` 查询也没有范围分批。

建议：所有分支共用有限大小的写入缓冲，只写变化；大规模清洗计划落临时 SQLite 或按游标分块。BOM 日常回填可优先处理本次 BOM、缺失字段和销售订单发生变化的订单，另保留历史修复入口。

### 14. [P2] 交付明细预检与写入读取两次源，校验并不覆盖实际写入内容

位置：`scripts/sync/sales_order_delivery_records.py:57`、`:71`；`scripts/sources/hana/hana_view_sync.py:477`。

预检成功后再次查询 HANA，并关闭第二次的源键校验。两次读取间若发生源变化，实际写入数据可能包含预检未见的冲突；同键不同内容使用 unordered upsert，最终内容不能由预检保证。两次全量读取也重复增加源负担。

建议：只读一次并落盘校验，使用同一份已校验快照写入，沿用维修 SQLite 快照的原则；校验重复内容与同键冲突分别计数。

## 减少重复代码与功能

建议保留每个数据源的明确入口，共用小型基础组件；不把所有业务揉成一个通用同步函数。

1. **公共运行基础**：统一配置、MongoDB URI/客户端、可续租锁、错误摘要、日志、批量缓冲和运行上下文。现有 HANA 模块包含不少与 HANA 无关的工具，可移到独立 runtime 模块。
2. **公共 SAP 客户端**：端点、签名和响应校验重复在销售脚本与维修脚本，空结果判定已经不同；方法与来源作为参数，保持业务处理独立。
3. **公共 SCS 会话**：两个 SCS 脚本重复登录与请求包装；复用一个可配置节流、重试、页面校验的客户端，DOA/换上换下的解析与业务键保持独立。
4. **公共订单匹配**：工位清洗、维修回填、BOM 日期回填分别构建销售订单映射。共享订单号规范化、日期规范化和“唯一候选/歧义”结果，业务回填优先级由各任务决定。
5. **分离维修实现**：把 repair_snapshot、sync_repair、finalize_repair_run 从销售订单入口移到维修模块，避免维修入口反向依赖销售任务模块。
6. **唯一任务目录**：Python TASKS 与 Go managedSyncTasks 两份定义，改为同一份任务描述或由后端消费 Python tasks 输出，并验证依赖和模式能力。
7. **移除无调用旧入口**：hana_view_sync.run_cli、watermark_max、fetch_changes 目前没有生产调用，部分只有测试使用；迁移实际外部调用后再删除兼容函数和对应无业务价值测试。
8. **精简参数与文档**：维修 one-click 默认开启时，多个启用 fallback 的参数重复表达默认行为；兼容参数应标弃用期限。根 README 仍写“不删除维修记录/推进旧水位”，与当前滚动快照实现冲突，应统一引用 scripts/sync/README.md 的维护说明。

## 建议实施顺序与验收
